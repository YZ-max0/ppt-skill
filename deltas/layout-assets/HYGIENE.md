# 骨架卫生标准（HYGIENE）

> T-FIX4 产出 ｜ 适用：`deltas/layout-assets/` 全部 24 骨架 + 任何由骨架填充的产物
> 定位：把"骨架示例内容泄漏"（C-011）从个案修复升级为**全库标准 + 自动化阻断**

## 1. 问题定义

骨架里的文本分两类：

| 类型 | 形态 | 填充时行为 |
|---|---|---|
| **槽位文本** | `【槽位名】示例内容` | 整段元素被替换 → 安全 |
| **无标记文本** | 裸示例数据 / 品牌字 / 示意标签 | **机械填充碰不到它** → 原样进入交付物 |

**C-011（真实事故）**：`v2/cover-bold` 把 T-03 的示例品牌字 `KB` /
`知识库平台建设方案` 放在无标记的 `<g id="bold-mark">` 里。填充后它们被带进 T-02 交付物，
封面出现上一个 deck 的品牌信息。

**为什么 checker 与 D-2 都拦不住**：这些文本在几何上完全合法（不越界、不缺失、
字号一致），属**内容泄漏**而非结构错误，落在既有质量门的检查域之外。
唯一可靠的原始发现方式是**渲染后人工看图**。本检查器把它变成自动断言。

## 2. 全库扫描结果（T-FIX4 R1）

修复前扫描 24 骨架，共 **43 个无标记文本元素**，其中 **24 处高风险（HIGH）**，涉及 7 个骨架：

| 骨架 | 元素组 | 原无标记内容 | 风险 | 处置 |
|---|---|---|---|---|
| `v0/kpi-hero` | `kpi-row` | `88%` / `156` / `99.4%` | HIGH | → `【值1】`/`【值2】`/`【值3】` |
| `v1/budget-4` | `budget-row` | `40 万`/`20 万`/`12 万`/`8 万` | HIGH | → `【金额1】`…`【金额4】` |
| `v1/process-steps` | `step-flow` | `1`/`2`/`3`/`4` | HIGH | → `【步骤一序号】`…`【步骤四序号】` |
| `v2/cover-bold` | `bold-mark` | `KB` / `知识库平台建设方案` | **HIGH（C-011 源头）** | → `【标识】`/`【标识说明】` |

| 元素 | 位置 | 理由 |
|---|---|---|
| `01`–`05` | `toc` / `decision-3` / `three-card` / `bullet-list` / `section-hero` | 版式固有编号，不表达内容 |

**修复后复扫**：HIGH = **0**，无标记文本元素由 43 → **19**（全部为上述结构性元素）。

### 2.1 修复时踩到的坑（R2b）

首轮把完整槽位名（如 `【指标三值】`）放进 **96pt 大字号列**，标记文本本身超宽 →
checker 报 `横向溢出 35.4%`（blocking）。这说明**大字号列对槽位名的长度也有约束**：

- 96pt（`kpi-hero`）→ 槽位名须极短，用 `【值1】`（约 336px）
- 64pt（`budget-4`）→ `【金额1】`（约 256px）
- 56pt（`evidence-wall` / `donut`）→ `【证据1值】` / `【中心值】`

**结论**：给大字号元素加槽位时，**槽位名长度本身也是几何约束**；
`v2/CONTRACT.md` §2.5"最坏文案验证"应把"槽位名 + 最长示例值"一起量。
另有两处 bounds 元数据过窄（`kpi-row` 右边界 1200、`budget-row` 同），
已放宽到画布右缘 1280——**只改 bounds 元数据，不动任何可视元素**。

## 3. 检查器用法

```powershell
# A. 交付物模式（默认）—— 检查"已填充的产物目录"，词表命中即 P0
python deltas\layout-assets\check_hygiene.py "<项目>\svg_output"
python deltas\layout-assets\check_hygiene.py "<项目>\svg_output" --json -o hygiene.json

# B. 骨架模式 —— 扫描骨架库，额外对"无标记元素"启用启发式
python deltas\layout-assets\check_hygiene.py deltas\layout-assets --skeleton-mode
```

**退出码**：`0` = 干净 ｜ `2` = 发现泄漏（P0）

### 两种模式为什么判据不同

| 模式 | 场景 | 判据 |
|---|---|---|
| **交付物模式** | 已填充产物 | **只用词表**。填充后所有标记都被真实内容替换，再无标记可依据；若叠加启发式，会把 `2024`、`全年净增 18 人` 这类**合法内容**误判（实测踩到） |
| **骨架模式** | `layout-assets/` | **元素粒度 + 词表 + 启发式**。含 `【` 的元素跳过（必被替换）；无标记元素再判：命中词表 / 大写品牌字 / 数字+单位 / 中文≥2 字 |

## 4. 示例词表（DEFAULT_TERMS）

词表收录"**只可能来自骨架示例**"的短语——真实内容不会恰好出现，故命中即可判定泄漏。
增补方式：把新发现的无标记示例内容追加进 `check_hygiene.py` 的 `DEFAULT_TERMS`，
或用 `--wordlist my.txt` 外挂。

| 来源骨架 | 词条 |
|---|---|
| `v2/cover-bold` | `知识库平台建设方案`、`知识库`、`KB` |
| `v0/kpi-hero` | `99.4%` |
| `v2/evidence-wall` | `软件、实施、硬件与培训四项合计`、`按找资料与返工工时折算`、`按上述节省口径推算得出`、`两项风险均有明确对策` |
| `v1/budget-4` | `平台软件与许可`、`账号打通与数据迁移工作量` |
| `v1/process-steps` | `支持按标题与正文检索`、`仅返回有权查看的资料` |
| `v2/donut-chart` | `软件与实施占预算四分之三` |
| `v2/line-chart` | `累计净投入随节省逐年下降` |
| `v1/layered-arch` | `统一检索层`、`权限控制与知识沉淀` |

> ⚠️ **新骨架入库时必须同步**：若新骨架含无标记示例内容，把该内容加入词表；
> 并跑 `--skeleton-mode` 确认 HIGH=0。

## 5. 预防规则（给未来骨架）

1. **任何会被导出为可见内容的文本，都必须带 `【槽位】` 标记**——包括数字、品牌字、图示标签。
2. 只有**版式固有元素**（序号、`对策`、引号等）可以无标记；新增此类须审查是否真属"固有"。
3. 大字号元素加槽位时，**槽位名长度也是几何约束**（见 §2.1）。
4. 新骨架入库流程增加一步：`check_hygiene.py --skeleton-mode` 必须 **exit 0**。

## 6. 已知边界

- 交付物模式**依赖词表**：词表未覆盖的新示例内容不会被发现（需按 §4 增补）。
- 骨架模式的启发式（中文≥2 字）在**版式固有中文标签**上会报 P1；当前 24 骨架已确认无此类误报。
- 检查器只查 **SVG 文本**，不查图片内嵌文字（本库骨架无图片）。
- 它是**内容层**补充，不替代 `svg_quality_checker`（几何层）与 D-2（出框/标题层）。
